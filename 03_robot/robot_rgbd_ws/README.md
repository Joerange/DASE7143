# Bunker Mini：RGB-D + YOLO + PID

独立工作区 `robot_rgbd_ws`，独立包 `bunker_rgbd`，默认 ROS 域 **182**。
不修改、不依赖 `robot_nav_ws`，不启动激光雷达、SLAM、Nav2 或云端模型。
只复用底层 `~/ros2_ws` 中已安装的相机/底盘依赖，以及现有本地 YOLO 权重。

## 主任务

`手动开始 → 原地搜索 → 锁定垃圾桶 → PID 转向/靠近 → 30 cm 停车 → 停稳完成`

1. 小车以 `0.12 rad/s` 原地旋转；YOLO 将模型中的 `trash can`、`garbage bin`、
   `waste bin`、`dustbin` 和 `recycling bin` 都视为垃圾桶目标。置信度阈值为0.40，
   窗口显示模型实际返回的类别。跨类别NMS合并同一个垃圾桶的重叠框。
2. 锁定第一帧中首个识别出的垃圾桶，不按最近或最高置信度重新排序，不等待转满一圈。
   同一帧有多个候选时沿用YOLO原始输出顺序；锁定后不切换到其他目标。
   首个目标没有有效深度时停下等待其深度，不改选第二个目标或猜测行进距离。
3. YOLO框内的深度表面点经相机外参变换到 `base_link`。
   目标方位 `atan2(y,x)` 给角度PID；剩余距离 `gap-0.30` 给距离PID。
4. 偏角大于 `0.12 rad` 时只转向；对准后边慢速前进边修正方向。
   可见时每帧更新角度和深度误差。锁定时还记录里程计坐标中的停靠点：
   方向为当前朝向+目标偏角，行进距离为到目标表面的距离减去车头长度和0.30m。
   中途目标框消失/遮挡/出视野，保持原目标，改用剩余里程计距离与目标方向继续PID行驶。
   YOLO结果暂时过期时也沿用该方式，旧检测框不参与方向或距离修正；独立深度、里程计和底盘反馈仍须有效。
   不需要地图；里程计反馈会不断修正行进量，并非按固定时间开环前进。
5. 距离PID输出前进速度，角度PID输出角速度。前进上限 `0.08 m/s`，
   净距小于 `0.65 m` 后上限 `0.035 m/s`；正向低速下限 `0.015 m/s`。
6. 在30cm目标附近考虑当前速度与制动延迟提前发零。目标可见时需要新鲜距离落在
   `0.27–0.34 m`，且里程计连续静止0.7秒才DONE；这是初始软件容差，现场尺测后收紧。
   若目标仍不可见，则在记录的停靠点附近停稳，完成依据标记为 `odometry_estimate`，
   表示按既定距离估计到位，不声称已经用深度确认30cm。
   不自动倒车修正。不因暂时停住而自动宣称任务完成。

YOLO提供类别、框和目标身份，**米制距离来自深度相机**。
30cm是物理车头到垃圾桶表面的净距，不是相机光轴深度。
车头参考 `base_link x=0.345 m`；使用目标有效表面点的前向距离10%分位数，
避免单个噪点决定停车，又比框内平均距离保守。

初始PID参数（P/I/D）：距离 `0.45 / 0.01 / 0.02`，角度 `0.70 / 0.02 / 0.04`。
有输出限幅、积分抗饱和和微分滤波；参数位于 `bunker_rgbd/core.py`。
这些是初始低速参数，尚未经实车调参，不声明实际停车精度已经达标。

## 简单实现结构

| 进程 | 功能 |
|---|---|
| `perception` | RGB-D同步、YOLO、本地身份关联、目标方向和净距；只保留最新待处理帧 |
| `mission` | 20Hz SEARCH/APPROACH/VERIFY_STOP/DONE/HOLD状态机和两个PID |
| `guard` | 独立50Hz最终速度出口；相机数据过期、异常指令、前方障碍时输出零 |
| `task.launch.py` | 统一管理本次相机、底盘和任务进程，窗口退出后清理本次启动的进程 |

只保留运行需要的基本检查：相机/目标/速度反馈新鲜，控制指令不过期，前方深度通道有效。
底盘里程计用于搜索角度、速度反馈和停稳确认，不参与地图定位。
由于现有底盘驱动会重复发布缓存状态，启用实车控制时guard还被动接收can0反馈，
用于识别通信中断；它不配置CAN、不发送CAN帧、不启动底盘。
AGX V2速度及故障码按高字节在前解码，与底盘SDK保持一致；出现速度不一致时，
日志同时打印CAN与里程计的具体数值，安全状态也分别回报两组速度。

前方障碍保护使用当前深度点，不做路径规划或绕行。目标框消失时按已记录目标继续；相机断流、深度保护区域无效或前方堵塞则HOLD。单个前向相机没有车侧/后方完整视野，搜索前需人工确认旋转空间；
适用可见目标、前方通路清晰的受控场地，不承诺任意障碍环境自主导航。

相机配置沿用D455的640×480、30fps及现有近似安装外参。
厂家数据表中该深度分辨率的Min-Z约0.32m；由于相机位于车头后方，
车头净距0.30m时相机到目标通常更远，但仍需检查真实有效深度与外参误差。
参考：[RealSense D400数据表，Minimum-Z Depth表](https://www.intelrealsense.com/wp-content/uploads/2024/10/Intel-RealSense-D400-Series-Datasheet-October-2024.pdf)。

## Jetson一键启动

在Jetson连接屏幕的图形桌面中，打开一个**没有source旧导航工作区的新终端**：

```bash
~/robot_rgbd_ws/scripts/run_task.sh
```

不需要另开终端或手动source。脚本启动相机、可视化窗口、任务、安全节点和
`bunker_base_node`（`port_name=can0`、`is_bunker_mini=true`），初始运动许可关闭，任务不自动开始。
脚本沿用已经配置好的can0，仅读取UP状态，不重新配置CAN、不调用sudo。
已有底盘驱动运行时会拒绝再启动一份；旧导航/相机任务应先由操作员退出，脚本不会杀掉其他工作区进程。

点击 `Bunker Mini` 窗口使其获得键盘焦点：

| 按键/操作 | 行为 |
|---|---|
| **S / Enter** | 请求安全节点授予运动许可；只有成功后才调用任务开始服务 |
| **空格 / X** | 立即请求禁用运动及停止任务；窗口保留，可再次按S开始新一轮 |
| **Q / Esc / 窗口右上角×** | 请求禁用运动、停止任务，等待停车反馈，再退出本次启动的全部后台进程 |

窗口启动即显示，等待相机/检测模型时也可退出。画面显示同帧检测框、类别、置信度、ID和车头净距；
锁定目标黄色、其他目标绿色。顶部显示任务状态、服务请求结果和安全节点阻塞原因。
可见目标使用 `visual_depth`，目标消失后显示 `recorded_odometry_goal`。
任务状态到达 `DONE` 后，画面中央持续显示醒目的英文 `TASK COMPLETED`；开始下一轮后自动清除。
窗口标题和屏幕状态文字使用通用检测描述，不显示算法名称。
S被拒绝时显示实际原因，条件恢复后需要再次按S，不会自动授权或续跑。

“Stopped”要求任务已退出、guard回报未授权且输出零、新鲜里程计及被动CAN反馈连续静止0.7秒。
停止结果超过15秒仍无法确认时显示 `Stop result UNKNOWN`，不把服务返回或进程退出称为停稳。
如果此时正在退出窗口，仍清理本次进程，并在终端留下结果未知提示；必要时使用实体急停。
退出不关闭can0，不终止本次启动以外的进程；ROS域隔离不等于物理CAN隔离。

窗口使用异步服务，显示限10fps并仅保留最新待绘制帧；独立50Hz保护不依赖窗口刷新。
窗口进程意外退出时，launch留出3秒供guard超时发零，再关闭本次进程。
S授权成功后，窗口等待任务节点回报 `start_ready` 再发开始请求，避免授权状态尚未送达造成偶发启动失败。
窗口及ROS日志保留实际任务停止原因，不再只显示“任务已开始”。

运行超时按要求统一设为原值的3倍，集中定义在 `bunker_rgbd/timing.py`：

| 超时项目 | 原值 → 当前值 |
|---|---|
| RGB、深度、YOLO、里程计、状态及CAN反馈新鲜度；目标ID保留 | 0.3 → 0.9秒 |
| 速度请求新鲜度、单次CAN接收等待 | 0.2 → 0.6秒 |
| 启动服务等待 | 3 → 9秒 |
| 停止确认、推理线程退出、进程信号等待 | 5 → 15秒 |
| 搜索时限 | 65 → 195秒 |
| 整轮任务时限 | 150 → 450秒 |
| 窗口进程退出后的清理宽限 | 1 → 3秒 |

| 窗口动作 | 实际接口 | 结果回读 |
|---|---|---|
| S开始 | `/rgbd/safety/set_motion_enabled` SetBool true → `/rgbd/mission/start` Trigger | 服务响应、`/rgbd/safety/status`、`/rgbd/mission/state` |
| 空格停止 | `/rgbd/safety/set_motion_enabled` SetBool false + `/rgbd/mission/stop` Trigger | 上述状态、`/odom`、guard的 `feedback_live/feedback_stopped` |
| Q/关闭 | 同停止流程，随后退出perception并触发ROS launch关闭 | 实际停稳检查、进程退出日志 |

窗口从不发布 `/cmd_vel`。只有guard发布最终Twist；没有地图、雷达或云端依赖。
原导航控制台没有改动；其旧按钮不会操作本工作区。

仅看真实相机、不启动底盘、不允许运动：

```bash
~/robot_rgbd_ws/scripts/run_task.sh --monitor
```

仅模拟画面、不启动相机/CAN/底盘、不允许运动：

```bash
~/robot_rgbd_ws/scripts/run_task.sh --demo
```

两种模式都使用 `/rgbd/cmd_vel_preview`，S不会获得实车运动许可；关闭窗口同样清理会话。
旧 `run_monitor.sh` 等价于 `run_task.sh --monitor`。

修改源码后只需重新执行一次 `~/robot_rgbd_ws/scripts/build.sh`。本次交付同步后会完成构建。

## 最小验证

```bash
PYTHONPATH=src/bunker_rgbd python3 -m unittest discover -s tests -v
```

19项关键逻辑回归：搜索/PID/目标保持/故障停车、窗口授权顺序、停止时取消开始链、
关闭时无法确认停车、五种垃圾桶类别、YOLO延迟时沿用记录目标、三倍超时边界，以及非零正负CAN反馈解码。
`scripts/check_can_decoder.py` 在临时目录编译实际底盘SDK的C解析器，用9组固定报文交叉校验Python解码结果；
只在内存中处理报文，不打开CAN、不启动驱动、不发送运动指令。
`scripts/smoke_window.py` 使用明确标注SIMULATED的画面在Jetson图形桌面验证真实Humble服务、
S被拒绝、空格停止、窗口×关闭以及所有本次子进程退出；不连接硬件。
验证结果见 `validation/RESULTS.txt`。真实PID参数、深度误差与尺测停车效果待现场验证。

独立复制并适配了原工程的深度表面提取与只读CAN解码函数（Apache-2.0），
运行时不导入旧工作区。本任务写入限定新工作区；只读摘要观察保存在 `validation/nav_ws_observation.json`。
该文件记录到旧工作区有并行变化，本任务没有写入或回退那些变化。
